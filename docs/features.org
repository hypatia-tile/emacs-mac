#+TITLE: Features and Setup Notes
This document records what is configured in =init.el=, the key bindings,
and the reasoning / verification behind the less obvious setup. It is a
companion to the inline comments in =init.el= and the operational notes in
=../README.org=.

Personal bindings stay within standard Emacs keys (no macOS Super/Command
leader). Where a package is a strict upgrade it replaces the standard key in
place: =C-x b=, =M-y=, =C-s=, =M-g g= now run the consult versions (plain
isearch-forward moved to =M-s s=). List every personal binding with
=M-x describe-personal-keybindings=.

*xref navigation:* the default keys -- =M-.= definitions, =M-,= go-back, =M-?=
find-references. (=M-,= had been shadowed by AeroSpace's =alt-comma= window
binding, not by Emacs; freeing it in AeroSpace fixed it. =M-?= was previously a
leftover help rebind -- help stays on =C-h=.)

*Bookmarks:* the built-in bookmark system is used (=C-x r m= set, =C-x r l=
list), with =C-x r b= upgraded to =consult-bookmark= (preview + create).
Bookmarks persist to =~/.emacs.d/bookmarks= (gitignored; personal locations).

* Completion and LSP
Two independent completion layers, by design:
- *Minibuffer* -- vertico + orderless + marginalia + consult (for =M-x=,
  find-file, buffer switching, search commands).
- *In-buffer* -- corfu shows a popup at point for =completion-at-point=,
  including eglot's LSP candidates. It pops up automatically while typing.

=eglot= (built-in) auto-starts a language server (=eglot-ensure=) in =c-mode= /
=c++-mode= (clangd) and =rust-ts-mode= (rust-analyzer). It wires the standard
Emacs facilities: eldoc (hover), flymake (diagnostics), xref
(definitions/references), and =completion-at-point= (shown by corfu). clangd
reads =compile_commands.json=; servers are found via PATH (exec-path-from-shell)
or the project's flake (envrc).

Rust uses the built-in =rust-ts-mode= (tree-sitter). Its grammar is not shipped
with Emacs, so =init.el= registers the grammar source and installs it once if
missing (only under a window system, so the batch health-check stays offline).
The compiled grammar lands in =tree-sitter/= (gitignored). If a =.rs= buffer
is not fontified, run =M-x treesit-install-language-grammar= for =rust=.

Diagnostics navigation: modern flymake ships no default keys and =M-g n= /
=M-g p= (next-error) are not wired to flymake, so they are bound explicitly
under the classic =C-c != prefix: =C-c ! n= next, =C-c ! p= previous, =C-c ! l=
list buffer diagnostics.

A *nixpkgs-built* Emacs puts every flymake backend behind =trusted-content=,
and an undeclared buffer does not get a skipped backend but a *disabled* one:
=Disabling eglot-flymake-backend in FILE (untrusted content)=, =Flymake:!= in
the mode line, and no diagnostics whatsoever -- type errors included (issue
#3).

This follows the packaging, not the version. Upstream Emacs gates only
=elisp-flymake-byte-compile=, the one backend that evaluates what it checks;
=flymake.el= upstream has no such check and =flymake-always-safe= exists
nowhere in the upstream tree. Both come from nixpkgs' =CVE-2024-53920.patch=,
which rewrites =flymake--run-backend= to gate every backend -- verified against
the Emacs 31.1 source nixpkgs builds from. The Emacs here, from Homebrew, never
reads the property, so the line in =init.el= is inert on this machine; it is
set for the NixOS machine that shares this configuration.

=init.el= puts =flymake-always-safe= on =eglot-flymake-backend= rather than
declaring trees in =trusted-content=: eglot's backend evaluates nothing, and
eglot has already started the language server on the file without consulting
=trusted-content=, whereas a declared tree would also let
=elisp-flymake-byte-compile= expand macros in every third-party clone under ghq
root.

Worth remembering when this is next debugged: a backend that signals goes on
the buffer's disabled list and is *not retried*. Setting the property in a
session where it has already failed changes nothing until =flymake-mode= is
toggled or =flymake-start= is called with a prefix argument. The =!= in the
mode line is clickable and leads to =flymake-switch-to-log-buffer=, which keeps
the reason a backend was disabled.

Buffer-word completion: the built-in =dabbrev= (=M-/=) completes the word at
point from buffer contents. To also get buffer words in the corfu popup,
=cape= registers =cape-dabbrev= (buffer words) and =cape-file= (file paths) on
the global =completion-at-point-functions=. These show up in ordinary buffers;
in eglot (LSP) buffers eglot installs its own buffer-local capf, so LSP
completion stays primary there (merging buffer words into LSP buffers with
=cape-capf-super= is deferred).

* Formatting (=C-c f=, Biome via apheleia)
The Next.js projects run [[https://biomejs.dev/][Biome]] as their formatter and linter: =@biomejs/biome=
in =devDependencies=, =biome.json= at the repository root. Emacs has to use
that same Biome, because the alternative -- =eglot-format-buffer=, which asks
the language server -- means tsserver's own formatter in a TypeScript buffer,
and that one formats by its built-in defaults and never reads =biome.json=.
Two formatters with different opinions on the same file is a diff on every
save, so only one of them can win.

=apheleia= runs the formatter in a subprocess and applies the result as a
diff, so point, the mark and the scroll position survive a save. Its built-in
=biome= recipe is:

: biome check --write --linter-enabled=false --stdin-file-path FILE

=check= with the linter switched off means format plus the =assist= actions
(=organizeImports= in these projects), and no lint fixes -- linting stays a
separate concern, and one Emacs deliberately stays out of: =pnpm biome lint=
on the command line is enough for it. Flymake here carries the language
server's diagnostics only.

** Finding the project's Biome
The recipe does not call =biome= directly; it goes through =apheleia-npx=, a
script bundled with apheleia that walks up to =package.json= and prefers the
project's own =node_modules/.bin/biome=. That indirection is needed here: the
flake dev shell provides =node= and =pnpm=, not the project's binaries, so
=biome= is never on PATH. In a project without Biome installed the script
exits 100, which apheleia reads as "formatter not available" and leaves the
buffer alone. Biome also leaves a file untouched when it cannot parse it, so
a buffer mid-edit is never mangled.

** Which buffers
=apheleia-mode= is hooked into =typescript-ts-mode=, =tsx-ts-mode=, =js-mode=,
=js-json-mode= and =css-mode= -- not switched on with =apheleia-global-mode=.
The global mode would also pick up apheleia's defaults for =rust-ts-mode=
(rustfmt), =c-mode= (clang-format) and =emacs-lisp-mode= (lisp-indent), and
format-on-save for those was never asked for. Add a hook when a language
actually needs one.

=js-json-mode= is named separately from =js-mode= because it is not a
derivative of it (its only parent is =prog-mode=). =.js= opens in
=javascript-mode=, an alias for =js-mode=, so that is covered; =.mjs= has no
=auto-mode-alist= entry at all in Emacs 30, so a =next.config.mjs= will need
one added.

** =C-c f= in a TypeScript buffer
=C-c f= is bound in =eglot-mode-map=, and a minor mode map wins over any major
mode map, so the key cannot simply be rebound per language. It now runs
=my-format-buffer=, which dispatches: apheleia where =apheleia-mode= is on (so
the key and the save hook run the same formatter), =eglot-format-buffer=
everywhere else -- Rust, LaTeX, C. =C-u C-c f= still reaches apheleia's
formatter prompt.

* Project switching (=C-x p p=, ghq)
Repositories are cloned with =ghq=, which owns the layout under =ghq root=
(=~/ghqrepo/<host>/<user>/<repo>=). The shell reaches them by piping =ghq list=
into fzf; the Emacs equivalent needs no extra package, because vertico +
orderless already do the filtering. Only the candidate list was missing.

=project.el= normally offers just the projects it has already visited, which it
persists to =project-list-file=. Instead, =project-prompter= (Emacs 30) is
pointed at =my-ghq-prompt-project-dir=, which shells out to =ghq list= on every
prompt. So =C-x p p= lists all ghq clones, a repo cloned a minute ago included,
and =C-x p f=, =M-s r= (consult-ripgrep) and the rest of the =C-x p= map then
act on the chosen project.

Repositories =ghq= does not manage are named explicitly in
=my-project-extra-roots= (currently =~/.emacs.d/= and =~/org-notes/=);
add a line when a new one starts to matter.

** Why no state on disk
=ghq list= is the source of truth, so project.el's own bookkeeping would only
duplicate it -- and duplicate it badly: =project-known-project-roots= returns
=abbreviate-file-name= paths with a trailing slash (=~/ghqrepo/.../repo/=)
while the ghq listing is expanded and unslashed, so the two spellings of one
repo never compare equal and both appear in the prompt. Rather than normalise
and merge the two lists, the record is switched off:

: (advice-add 'project-remember-project :override #'ignore)

=project-list-file= is left at its default (=~/.emacs.d/projects=) and the
file is gitignored, because the override does *not* stop it from being
written. =project-switch-project= -- the command behind =C-x p p=, the one
path this config actually uses -- calls =project--remember-dir= directly
rather than going through =project-remember-project=, so the advice never
fires and the file reappears holding whatever was switched to last. Its
contents are inert: the prompt is built from =ghq list= and nothing reads
the list back. Re-pointing the advice at =project--remember-dir= would make
the file genuinely stay absent; ignoring it was the cheaper choice.
Pointing it at =null-device= instead was rejected: project.el reads the file
back, and an empty one fails =read=, producing a "Failed to read the projects
list file due to unexpected EOF" warning.

** Project-local notes (=C-x p n=, =C-c c p=)
Notes that belong to one repository but not in its history live at the
project root as =.local.org=, with an optional =.local-note/= directory for
attachments and split files. Both paths are ignored by the global git ignore
in dotfiles-mac (=config/git/ignore=), so they never enter a clone; this
config only reads and writes them.

- =C-x p n= (=my-project-open-local-note=) visits =<root>/.local.org=. A
  missing file opens as an empty buffer and is written on the first save --
  merely looking does not leave a file behind.
- =C-c c p= appends a bare entry stamped with date and time, the same shape as
  the inbox template =i=.

Both resolve the file through =my-project-local-note-file=, which calls
=project-current= without prompting and signals a =user-error= outside a
project. The capture target is written as =(file my-project-local-note-file)=
-- a function, not a path -- so it is resolved on every capture, in the buffer
capture was started from, and can never fall back to a file under =$HOME=.
Verified both inside a git project (from a subdirectory) and outside one.

** Project of origin on inbox captures (=C-c c i=, =C-c c t=)
Inbox items are refiled later (=C-c C-w=) into =todo.org=, by which time the
buffer they were captured from is long gone. So when =i= or =t= is captured
from inside a project, the entry records it:

: * TODO fix the thing
: :PROPERTIES:
: :PROJECT: emacs-mac
: :END:

The templates embed =%(my-capture-project-drawer)= right after the headline
line (a property drawer is only recognised there). Outside a project the
function returns "", so no drawer and no blank line appear. The name is
=project-name= of the project, i.e. the repository directory name. A property
was chosen over a tag: it needs no rewriting of names (tags cannot contain
=-=), and once refiled under a project heading in =todo.org= it stays out of
sight instead of repeating that heading.

Two facts behind the implementation:
- =%(...)= is evaluated in a temporary =*Capture*= buffer, not the buffer
  capture started from. =project-current= happens to work there anyway,
  because the temporary buffer inherits =default-directory=; the function
  switches to =(org-capture-get :original-buffer)= so it does not rely on that.
- The expression must sit inside the template string. =org-capture-templates=
  is a quoted list, so a =(concat ...)= in the template position is stored
  unevaluated and capture reports "Invalid capture template"; a backquoted
  =,(...)= would be evaluated once at startup, not per capture.

Verified: =i= and =t= from a git project get =:PROJECT:=, which
=org-entry-get= reads back; =i= from a non-project directory gets none.

* Modal navigation (=my-nav-mode=)
A transient vi-style layer for the times when reading and moving dominate
over typing. =<escape>= enters it, =i= leaves it. Inside, the letter keys are
motions instead of self-inserting characters. It is hand-written (no evil, no
meow) and built entirely from stock Emacs commands -- see the =;;; Modal
navigation= section of =init.el=.

It is deliberately *not* a full vi emulation. There is no operator+motion
grammar (=dw=, =ciw=, =.=): =viwd= covers that case with one extra keystroke,
and the state machine such a grammar would need is exactly what this layer
avoids.

** Keys
| Group     | Keys                                                            |
|-----------+-----------------------------------------------------------------|
| Motion    | =h= =l= char, =j= =k= line, =w= next word, =e= word end, =b= back |
|           | =0= =^= =$= line, ={= =}= paragraph, =gg= top, =G= bottom / line N |
| Counts    | =1=-=9= then the motion: =3j=, =5w=, =10G=                      |
| Screen    | =C-d= =C-u= half screen, =zz= recenter                          |
| Selection | =v= start / cancel, =V= whole lines                             |
| Edit      | =y= copy, =d= cut, =p= paste, =P= paste from history, =u= undo  |
| Objects   | =iw= word, =is= symbol, =i"= string, =i(= brackets, =ip= paragraph, =if= defun |
|           | =a"= with quotes, =a(= with brackets (selection must be active)  |

=y= and =d= need a selection; without one they only print =No region -- press
v first=, so vi muscle memory (=d= then a motion) cannot delete a line by
accident.

** What =<escape>= does
One key, one meaning -- cancel, or enter the layer where text is normally
typed:
| Where                       | Effect              |
|-----------------------------+---------------------|
| Minibuffer                  | =abort-minibuffers= |
| Editing buffer, layer off   | enter the layer     |
| Editing buffer, layer on    | drop the selection  |
| Anywhere else               | =keyboard-quit=     |

Binding =<escape>= costs its role as the =ESC= (meta) prefix. =C-[= still
produces =ESC= and Option is meta on macOS, so the only practical loss is
=ESC ESC ESC= (=keyboard-escape-quit=) -- the last row above stands in for it.
vterm needs no special case: =vterm-mode-map= already binds =<escape>= to
=vterm--self-insert=, and a major mode map shadows the global one, so Neovim
running inside vterm still receives Escape.

** Three decisions worth remembering
- *=emulation-mode-map-alists=* -- the layer's keymap is registered there, not
  merely as a minor mode map, so it beats *every* minor mode map. ddskk's
  =skk-j-mode-map= binds =h= to =skk-insert=, and ddskk loads lazily, so
  registration order in =minor-mode-map-alist= would otherwise decide the
  winner. Because skk's own state is never touched, Japanese input simply
  resumes on exit.
- *=menu-item= =:filter= on =i= and =a=* -- with a selection active they are the
  vi "inner" / "around" prefixes; without one, =i= is the exit key.
  =(region-active-p)= already encodes "is a selection in progress", so the
  layer needs no state variable of its own. (Consequence: with a selection
  active you cannot leave with =i= -- press =<escape>= to drop it first.)

  This is where the layer's one external dependency lives: =region-active-p=
  is =(and transient-mark-mode mark-active ...)=, so the whole selection half
  -- =i= / =a= as prefixes, and =y= / =d=, which go through =use-region-p= --
  needs =transient-mark-mode= on. It is on by default in an interactive Emacs
  and nothing here turns it off, so this only bites in =emacs --batch=, where
  it defaults to nil. A batch test of =viw= consequently /looks/ like a bug in
  the text objects: =v= sets the mark, =region-active-p= stays nil, =i= is
  read as the exit key, and the rest of the sequence types itself into the
  buffer. Enable it explicitly in any batch test of this layer.
- *Cursor shape as the indicator* -- box while navigating, bar while typing.
  =cursor-type= is buffer-local, so no hook has to track the current buffer.
  Cursor /colour/ is a face, i.e. frame-wide, and would have needed one.

** Differences from vi, accepted on purpose
- No =dw= / =ciw= / =.= -- use =viwd=.
- No =x=; =d= always needs a selection.
- =is= is *symbol*, not vi's sentence. In code =my_variable= is one symbol but
  two words, and the symbol is nearly always what one wants.
- No =aw= / =as= / =ap=: =bounds-of-thing-at-point= excludes surrounding
  whitespace, so they would be identical to their =i= counterparts. Only the
  delimited things (=a"=, =a(=) differ.
- Text objects take no count (=v2iw= does nothing).
- =p= inserts at point; vi pastes after the cursor.

=i(= and =a(= do *not* use =bounds-of-thing-at-point='s =list= thing: inside a
string that reports the word at point rather than the enclosing brackets.
=(nth 1 (syntax-ppss))= is used instead -- a string is not a list to the
parser, so point inside one still finds the brackets around it.

** How the entry test recognises an editing buffer
The rule is "=a= still types an =a=", which keeps magit, dired, help and Info
out without maintaining a list of modes. Getting it right takes *two*
questions, not one (issue #2):

#+BEGIN_SRC elisp
  (and (eq (key-binding "a" nil t) 'self-insert-command)   ; fundamentally a text key?
       (not (eq (key-binding "a") 'undefined)))            ; and not switched off?
#+END_SRC

- The first clause passes =NO-REMAP=, so a mode that /customises/ typing still
  qualifies. org-mode remaps =self-insert-command= to =org-self-insert-command=
  for table auto-alignment; the original single-clause test asked only for
  =self-insert-command= and therefore locked org buffers out entirely. This
  clause is also what rejects dired, which binds =a= outright
  (=dired-find-alternate-file=) rather than by remapping.
- The second clause reads the remap. =suppress-keymap= -- which the special
  modes use, and which =my-nav-mode-map= applies to itself via
  =defvar-keymap :suppress t= -- disables typing through that same remap,
  pointing it at =undefined=. Reading where the remap leads is the only way to
  tell "customised typing" from "no typing".

Two rejected alternatives, recorded so they are not re-attempted:

- =NO-REMAP= *alone* is not the fix. It would let =<escape>= into
  =special-mode=, =help-mode= and magit, for exactly the reason above.
- =(derived-mode-p 'text-mode 'prog-mode)= is not usable either: =conf-mode=
  (=.envrc=, config files), =fundamental-mode=, =comint-mode= and =eshell-mode=
  derive from neither and would all be excluded.

Verified across every mode in this config -- entering in =text=, =org=,
=emacs-lisp=, =lisp-interaction=, =fundamental=, =conf=, =prog=, =rust-ts=,
=typescript-ts=, =LaTeX=, =comint= and =eshell=; staying out of =special=,
=dired=, =help=, =Info=, =Buffer-menu= and =tabulated-list=.

** Tuning the keys
=defvar-keymap= has =defvar= semantics, so =C-M-x= on the keymap does not
update an existing binding. Either evaluate =(keymap-set my-nav-mode-map "..."
#'...)= directly, or =M-x restart-emacs=.

* Per-directory environments (nix flake + direnv)
This machine uses =direnv= + =nix-direnv= with a =.envrc= (=use flake=) per
project directory. Two independent paths make those environments work inside
Emacs:

- *Inside vterm* -- vterm runs =$SHELL= (zsh), whose direnv hook loads the
  directory's =.envrc= automatically. Nothing Emacs-specific is needed.
- *Emacs-native commands* (=compile=, =eglot=, executable lookup) -- these do
  not go through the shell, so =envrc= applies the =.envrc= environment
  buffer-locally instead. This is what feeds the flake toolchain (e.g. clangd)
  to eglot -- see the Completion and LSP section.

Prerequisite: a GUI Emacs on macOS starts with a minimal PATH and cannot see
=direnv= / =nix=. =exec-path-from-shell= imports the login shell's PATH so
=envrc= can find =direnv=.

*Gotcha:* a new or changed =.envrc= must be approved once with =C-c e a=
(=envrc-allow=) before Emacs will apply it.

** Verified working (2026-07-28)
- =envrc= applies a directory's =.envrc= to Emacs buffers (checked that a
  project's flake variables appear via the minibuffer, e.g. =M-: (getenv ...)=).
- =vterm= runs a full terminal inside Emacs -- Neovim launches inside it and
  its LSP works, confirming vterm is a real PTY.
- =vterm='s native module builds via cmake/libtool and is pre-compiled.

* Background transparency (=alpha-background 0.70=)
Calibrated against kitty, which runs =background_opacity 0.90=. The two numbers
do **not** correspond: =alpha-background 0.90= looks very nearly opaque next to
that terminal, and 0.70 is what reads as the same weight. Whatever the two
parameters multiply is evidently not the same quantity; it was set by eye and
not chased further.

#+begin_src emacs-lisp
(add-to-list 'default-frame-alist '(alpha-background . 0.70))
(add-to-list 'default-frame-alist '(ns-alpha-elements ns-alpha-all))
#+end_src

** Why two parameters, and why it did not work before
The built-in =alpha-background= does nothing on this macOS on its own. Four
Emacsen were tried and none rendered it: emacs-plus 30.2, emacs-mac 30.2.50, and
the stock Cocoa build of 31.1. It is not a configuration problem and no setting
here fixes it.

What makes it render is a C patch reaching the CGS APIs -- =frame-transparency=
from the =d12frosted/emacs-plus= tap (maintainer =aaratha=). It exists for Emacs
31 only and patches the NS port, so it applies to the standard upstream Emacs,
and it is carried by the Emacs this configuration now runs on:
[[https://github.com/hypatia-tile/emacs-flake][hypatia-tile/emacs-flake]], adopted
in dotfiles-mac ADR 0031. Confirmed rendering 2026-09-27.

=ns-alpha-elements= is that patch's own parameter and selects what the alpha
applies to. **With it unset nothing is transparent**, however low
=alpha-background= goes, which is the trap if only the familiar parameter is set.
=ns-alpha-all= is every element; the patch also offers =ns-alpha-default=,
=-fringe=, =-box=, =-stipple=, =-relief= and =-glyphs= to choose from, which is
where to start if the region or =hl-line= reads badly through the window.

Both lines are inert on an Emacs without the patch rather than wrong, so the
configuration stays portable.

** Why =default-frame-alist=, and no blur
=default-frame-alist= rather than =set-frame-parameter=, so a frame made later
comes up the same. No hook is needed here; the patch's own README adds one for
its =ns-background-blur=, which configures the NSWindow backing material at frame
creation time and therefore cannot be applied to a frame afterwards. This Emacs
is not a daemon either, so there is no second frame-creation path to cover.

Blur is deliberately left off. Transparency alone is what matches the terminal,
and =ns-background-blur= is available if that judgement changes.
